Read the system before you change it.

The practice has four rules. They describe how a change should go. They are not a history of past jobs.

  1. 01

    Read the system before changing it.

    Open the paths a person actually uses. Write down what the code does today. A change that skips this step fixes a guess.

  2. 02

    Name the constraint.

    Say what the work will not do. Write the limit where the next person will see it. A hidden limit comes back as a late surprise.

  3. 03

    Leave the next person a map.

    Record the names, the decision, and the reason. A map is a note someone can follow without you in the room.

  4. 04

    Prefer boring reliability, then make the interface clear.

    Keep the system steady first. After it holds, make the screen say what is happening. Clarity is the second pass.

Ship the smallest true thing.

Method

Order matters. Reliability before a clearer screen. A clearer screen before a new idea.

Michael Watson states these as standards for the practice.
